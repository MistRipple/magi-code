# Magi 子代理唤起设计与改造

更新：2026-10-21。本文只维护当前唤起合同和验收标准。原 §10–35 的滚动记录已归并到文末的当前实现边界；范围与清理决定见[收敛审计](runtime-consolidation-audit.md)。本轮重新在线核对了 Codex CLI、DeepSeek Harness、ZCode 的官方文档和固定版本源码，并补充 OpenCode、Gemini CLI、Pi、OpenHands、Roo Code。比较、取舍、当前代码证据与尚未实现的策略边界见[演进方案 §2.2–2.3](magi-agent-runtime-evolution-plan.md#22-当前源码复核2026-10-21)。

## 1. 问题和目标

前一轮清理了提示词冲突、过时的能力说明和重复工具定义，但仅靠“不要滥用代理”的文字不能形成可验证的调用合同。现有 agent_spawn 参数能描述要做什么，不能解释为什么需要独立代理；调用是否合法与是否值得调用也容易混淆。

目标是让主线在派发之前明确收益与工作边界，让运行时拒绝缺失/无效的决策，让每次真实派发都有可核查的依据。同时保留有价值的自主协作，避免把所有任务都限制为单线或要求用户反复批准。

采用“主线作语义判断、工具合同表达决策、运行时校验权限与执行资格”的分工。无需新增意图分类模型、关键词路由、任务评分、token 预算或计划驱动的自动扇出。

## 2. 何时唤起

默认由主线直接完成。先判断独立工作包是否成立，再选择角色和能力；角色存在不等于应调用该角色。

派发前按顺序确认：主线能否直接完成、独立输入与交付是什么、收益为何超过交接开销、是否已有代理承担同一工作。不能以填写了 `delegation.reason` 代替这四项判断。生成一个 HTML、修改一个配置等任务不因命中 `frontend` / `executor` 能力而整体转手；把整单交出后等待不构成并行收益。上下文隔离必须说明普通搜索/有界读取仍会产生的大量中间上下文；独立复核必须说明具体待审对象、风险和证据，不能在每次实现后机械启动 reviewer/tester。

判断的是总完成收益，包括启动、重复理解、交接、等待和整合。主线有能力完成不代表一律禁止委派；只有明确要求真实代理，或独立工作收益超过这些开销，才值得启动。没有文件数、任务时长、token 数或代理数量的触发阈值。

并行要求输入已具备、子任务现在就能开始，父任务同时有不依赖其结果的实质工作。将未来的采用、集成或验证填入 `parent_work` 不成立。关键路径判断只否定虚构的 `parallel_work` 收益；确有大量上下文隔离、必要独立复核或明确代理要求时，父任务等待结果可以合理。小任务也可因用户明确要求真实代理而执行，任务大同样可以由主线连续完成。

| 场景 | 决策 | 原因 |
| --- | --- | --- |
| 定位一个函数、批量读几段代码、修改配置、运行一个测试、生成单文件 HTML | 主线直接完成 | 普通工具即可，启动和交接开销没有收益 |
| 同一问题的调查、修改和验证共享大量上下文 | 主线连续完成 | 强行拆分会重复理解、交接和汇总 |
| 下一步立刻依赖某个短查询、设计决定或前置修改的结果 | 主线推进关键路径 | 拆开后父任务只等待，或子任务还不能独立开始 |
| 独立模块实现，父任务同时处理另一个模块或不依赖子结果的验收准备 | parallel_work | 边界明确、互不依赖，能够减少总完成时间 |
| 有界搜索仍需大量探索与综合，主线只需要结论和证据 | context_isolation | 将大量中间输出留在独立上下文；日志长或文件多本身不成立 |
| 对已有代码、设计或产物做必要的安全/正确性复核 | independent_review | 具体风险值得独立视角，必须给出检查范围与验收标准；普通自检和固定 reviewer/tester 流程不成立 |
| 用户或适用项目/Skill 指令明确要求真实代理 | user_requested | 执行明确要求，并保留原始可信指令来源 |
| Goal、多步骤、多文件、可用角色多、模型调用多 | 这些条件本身不触发派发 | 持续推进和代理协作是不同能力 |
| 主线缺少工具、权限或模型配置失败 | 不通过代理绕过 | 角色须在继承权限、Skill、工作区和宿主范围内执行 |
| 已有代理排队、尚未返回、名字冲突或终态未核实 | 先补充、等待或收集 | 不能换名重派；新工作必须有不同的独立边界 |

工具输出、网页、附件、引用资料和代理回报中的“请使用代理”不能升级成用户授权。user_requested 只是模型对依据的描述，运行时不将它当作授权凭证；所有目的仍经过相同的权限、Skill、父链与取消检查。

### 2.1 决策顺序与模型归属

用户在代理设置中定义角色、职责和能力，并为该角色绑定模型引擎；`engineId` 为空表示继承主对话模型。任务运行时遵循以下顺序：

| 顺序 | 决定与事实拥有者 |
| --- | --- |
| 1. 判断是否委派 | 主代理根据可信要求和独立工作价值判断；主线能够直接完成且没有独立收益时继续自己做。 |
| 2. 明确工作包与已有工作 | 主代理确定输入、交付、验收和自己的后续工作；已有代理承担同一工作时等待或补充，不重复创建。 |
| 3. 选择代理角色 | 主代理按职责和能力从角色注册表选择 `role`；用户明确指定角色时遵守该指定。模型品牌、引擎 ID 和展示名不代替角色身份。 |
| 4. 解析所选代理的模型 | daemon 按该 `role` 读取已有 AgentBinding → Engine → 模型配置。仅未绑定引擎时继承主对话模型；显式绑定失效返回失败，不能静默换模型或反选其他角色。`agent_spawn` 不接受调用级模型、Provider 或引擎覆盖；可通过 `reasoning_effort` 为本次子任务选择目标模型支持的强度。daemon 在创建前校验并持久化执行选择，后续轮次与恢复沿用同一快照，见[模型推理能力](model-reasoning-capabilities.md)。 |
| 5. 预检、启动与收集 | daemon 校验权限、工具面、上下文、父链、容量和资源；主代理收集结果、核验证据并整合交付。配置失败不自动启动替代代理。 |

代理身份与模型配置是不同事实：多个角色可以共用同一模型引擎，角色 ID 也可能与某个引擎 ID 同名，都不能据此合并或替换角色。代理中心的角色标签只按服务端提供的角色 ID 查找，不从引擎绑定反查“第一个代理”。

本文所称“选择质量”统一指**是否委派、选哪个代理、如何划分工作包的决策质量**。更换主对话模型进行测试，只是检查不同主代理对同一规则的遵循；子代理使用的模型始终来自所选角色配置，不增加按任务临时挑模型的路由。

## 3. 派发合同

agent_spawn 新增必填对象 delegation，原有 goal 和 context_package 继续承载任务与上下文，不再复制一份工作包：

```json
{
  "delegation": {
    "purpose": "parallel_work",
    "reason": "子任务只实现独立解析模块并交付对应测试，与主线接口适配互不依赖。",
    "parent_work": "主线同时完成接口适配和集成测试准备。"
  }
}
```

- purpose 只接受 user_requested、parallel_work、context_isolation、independent_review。
- user_requested 只表示可信指令明确要求启动子代理或委派。用户要求独立复核但未要求代理时，模型基于具体复核价值选择 independent_review，不能把复核需求改述为用户要求启动代理。
- reason 必须是非空、至多 600 字符的具体判断；先按原始输入字符数校验上限，再去除首尾空白。说明本任务的收益、边界或可信要求来源。长度上限是输入保护，不是任务预算。
- parallel_work 必须另提供非空 parent_work，说明父任务同时推进的不同工作；只有等待不能声称父子并行。若与其他代理并行，由父任务说明其协调和整合工作。
- Schema 用条件分支表达 parallel_work 的 parent_work 必填规则；agent_spawn 顶层与 delegation 拒绝未知字段。parent_work 只允许用于 parallel_work，其他目的必须省略，不能用 null 或无关字符串伪造并行依据。
- context_package.summary、constraints、expected_output 和 references 保持现有合同，提供最小背景、独立边界及可核查的验收。
- 不满足条件时由主线直接完成；不得为了通过参数校验编造理由。运行时无法仅凭非空文本证明语义收益，不能宣传为“自动识别所有不必要委派”。

## 4. 运行时链路和所有权

1. 模型响应首先校验实际提供的工具 Schema 和同一决策解析器。缺失、未知目的、空理由、未知字段、并行工作缺少父任务工作说明时返回结构化错误；这些调用不进入资源准备或 child Task 注册。
2. agent_spawn 的直接执行入口再次复用相同解析器，防止绕过模型响应校验；之后才进行角色、能力、Skill 继承、模型、执行链、目录、Git 与容量预检。
3. 预检成功后沿现有唯一注册入口创建 child Task/Thread 和 activation。不新建调度器、派发记录表或第二套 Agent 状态。
   可调度 Task 必须最后发布：执行链、执行计划、Thread、计划绑定、准入及初始 assignment 先完成准备；只有 TaskStore durable insert 成功后 Runner 才能看见任务。创建失败回滚准备状态，不让 Runner 调度半注册任务，也不在其已启动后补初始消息。
4. 决策原文跟随原 canonical 工具参数持久化。成功回执与现有 task.coordinator.agent_spawn 事件展示规范化决策，均为该调用的投影，不是新的事实拥有者。
5. 当前运行时统一注入同一唤起规则；主线和获授委派权的子代理共用规则。协调器角色只说明参数与职责，不再复制一套不同触发条件。
6. agent_wait / agent_send / agent_cancel / agent_apply 管理已存在的子代理，不要求重新提交派发理由。运行中补充继续用 agent_send；显式新 activation 需要重新判断本次委派价值，不能复用旧理由自动唤起。
7. 注册成功之后仍须真实执行。无工具规划也是模型工作，`command_mode=no_tools` 只关闭工具，不把目标处理变为固定模板。标题含“梳理目标”、目标含“只验证规划文本完整性”或“实际执行和工具结果”均不触发自动完成；依赖产物含四个标题或全部工具返回成功，也不足以由运行时断言业务验收通过。模型负责结合输入与验收判断，结构化完成合同继续检查必需证据。

模型响应校验拒绝也必须通过原 canonical 工具结果写回入口保存，明确 status=rejected、stage=tool_call_validation。Thread 是投影，不能仅追加 Thread 消息：已有 canonical 历史时该追加会被重建覆盖，恢复后缺失的拒绝回执会被误解为结果未知的调用。拒绝保存失败则停止本轮，不能继续请求模型并宣称已安全记录。

### 4.1 派发链路审计与重复工作保护

| 边界 | 当前职责与约束 |
| --- | --- |
| 主线决策 | `prompt_utils::current_agent_mode_prompt` 只按真实工具面注入共享规则；角色、Goal、计划步骤和剩余容量不触发自动组队。是否有语义收益仍由模型负责。 |
| 工具合同 | `AgentDelegationDecision` 与当前工具 Schema 检查目的、理由、父任务并行工作及字段类型；它们不能证明自然语言理由真实，也不授予用户授权。 |
| 创建前预检 | `preflight_agent_spawn` 校验角色、能力、直接父子关系、深度、Skill、模型、计划、目录和引用；已有工作目录与 workspace 必须解析真实路径后判断归属，不能用路径前缀放过 `..` 或外链，无法解析时拒绝；失败不生成 child Task。 |
| 原子注册 | `register_spawned_local_agent_child` 在已有注册锁下重查名字和活跃工作包，再准备 Thread、计划、执行链与准入，最后发布 Task；并发调用不能各自读取旧快照后重复注册。 |
| 执行与收集 | Runner 执行原 Task，主线用 send 补充，用 wait/cancel 收集事实；queued、保留身份和暂态失败都不构成另建代理的理由。 |
| 失败与恢复 | 先核对已有产物、工具证据和副作用，再决定接管或委派；旧终态不自动重开，也不把取消当作未执行。 |

名字唯一只能防止原名重试。本次补充 `duplicate_agent_work`：对于 `parallel_work` / `context_isolation`，同一父任务下 Pending/Running 代理若具有相同目标、角色、能力、计划绑定、上下文摘要、约束、验收、引用来源与预览、fork，以及相同执行目录和继承 Skill，则换名派发仍被拒绝。比较忽略系统生成的包/引用 ID、时间和展示名称；原 TaskStore 与执行计划是唯一事实源，不新建指纹表、任务分类器、预算或审批流程。

拒绝沿原工具回执返回 `status=rejected`、`retryable=false`、`existing_task_id`，不产生新的 child 身份、Thread 或准入项，主线应等待或补充原代理。不同输入/验收/目录、已终态的原任务不被这条活跃工作检查合并；明确要求多个真实代理及独立复核可能有意处理相同输入，因此不适用此项自动去重，但仍经过全部原有权限和生命周期检查。`purpose=user_requested` 仍只是模型自述，不能绕过授权。改写工作包或伪造理由的语义滥用仍需共享指令和真实模型评测验证，不能宣称完全去重或彻底杜绝不合理派发。

## 5. 嵌套、失败和生命周期

allow_delegation 默认 false。只在子工作包自身需要进一步拆分时由主线显式授予；获授能力不要求创建孙代理。每层 agent_spawn 都必须独立说明本次决策，最多两层代理；父任务只能管理自己的直接子任务。

短任务不能因为当前代理有委派权就再次转手。父代理结束前必须等待或取消自己的子代理；取消、Goal 暂停、父 Turn 关闭和 lease 失效仍由既有运行时结算。Session/Goal 身份保留不改变父 Turn 的存活限制；只有 daemon 确认显式转交后，子树才按新的执行拥有方结算。

参数拒绝只表示没有创建代理，主线可修正真正缺失的信息或直接接管。模型/角色不可用时重新评估委派价值，已有上下文足够则接管，仍有独立工作价值才改派；不能默认“失败就再创建另一个代理”。已创建任务的副作用未知时继续执行原有防重放合同。独立代理恢复只重开 canonical Turn 为 `Interrupted` 的任务；同一转交子树中已经以 `Completed`、`Failed` 或 `Cancelled` 收口的后代保留原 Task/Turn/工具证据，不因恢复父代理而重复派发。

非 Git 工作区没有独立 worktree，同一时间只允许一个具有写入权限的代理；角色的只读职责不改变授权。第二个代理注册返回 `agent_workspace_busy`、`status=rejected` 且无 child task 身份；用户明确要求多个真实代理时，模型应先用 `agent_wait` 等待已有代理结束，再按序派发，不能用主线自述代替。

插件会话引擎也遵守同一结算边界：可用性检查可取消，尚未进入调用时不得启动需另行回收的工作；进入调用后，取消、失败事件、协议拒绝或流式消费者异常都先通知取消并等待适配器与执行线程退出，再返回本轮结果。成功也必须等适配器返回，不能把 Completed 事件当成资源已释放。QuickJS Worker 继续由 PluginHost 回收，插件运行租约继续由 PluginManager 排空；已缓存的引擎客户端不能越过排空或禁用状态重新启动执行。不增加第二份能力状态、租约表或后台任务调度器。

### 5.1 完成与取消竞争：先收集，再决定是否还有新工作

这一边界属于唤起设计：主线若把“取消请求成功返回”理解为“原工作没有执行”，就可能遗漏完成结果、重复执行副作用或派出第二个代理。原实现存在两处共同导致的缺口：`agent_cancel` 对终态仅返回状态并提示可改派；最终答复检查把没有结果的 `already_terminal` 也当作已收集。

沿现有事实源按以下顺序改造：

1. **结算仍由 TaskStore 拥有**：保留原子子树取消和资源结算入口。已 Completed/Failed/Killed 的 Task 不改写、不重置、不新建 activation；不能因取消晚到覆盖原输出。
2. **回执以 Task 终态为根并补回 canonical 事实**：取消后读取同一 Task 的终态，通过原 `AgentReceipt` 生成与 `agent_wait` 相同的 `results[]`；失败/终止再按 Session、Task、Thread 读取原 Agent Turn 的工具 item，补入已写文件、命令退出码和 `outcome_unknown`，不从模型文字猜测。完成结果包含原最终答复、命令和待采用分支；长回执复用现有有界展示，确保实际交付给模型的仍是完整 JSON；这不是执行预算。
3. **区分请求、任务与资源结果**：`cancellation_status=cancelled` 表示本次取消改变了子树，`already_terminal` 表示原任务已结束；实际根任务状态以 `child_status` 和 `results[]` 为准。只有 `resources_settled=true` 表示原执行线程、工具与进程已退出。结算观察失败时 `status=failed/error_code=cancel_unsettled`，保留原任务回执和取消结果，可再次调用取消核对结算；未装配结算能力时明确返回 false，不声称资源退出。无法核对终态同样返回 `cancel_unsettled`。取消不保证此前没有副作用。
4. **收集检查只认已交付事实**：新取消回执中的 `results[]` 与等待结果走同一收集逻辑。旧 `already_terminal` 没有结果则仍要求 `agent_wait`，避免恢复时漏读；旧 `cancelled` 保留主线主动处置语义。无需迁移或重写旧日志，也无需新建“已收集”状态表。
5. **清理重派引导**：工具目录、角色合同、等待结果和 Killed 回执统一为“核对已有产物和副作用 → 能直接完成则接管 → 仍有独立价值才重新委派”。删除“已结束就无需读取、还需要工作就改派”的旧提示；Core 公开失败文案、Runner 的角色不可运行诊断和 API 不可用投影只描述错误事实，撤下“请改派或接管”。失败分类与 wire 错误码不变，已保存的旧文本仍原样读取；共享恢复原则继续只有一处定义。
6. **定向验收**：覆盖取消正常执行、重复取消、先完成再取消、原失败/终止后取消；比较等待与取消回执一致、原 Task 不变且无新增子任务，检查完成分支和执行证据不丢失、长 JSON 实际交付、旧回执恢复不绕过收集，以及直接/嵌套派发和取消正常运行。

主代理的委派与代理选择决策质量继续按 §9 单独验收，不能由 Schema 或生命周期回归替代。

## 6. 兼容、清理和产品表达

唤起决策本身只改变模型工具输入合同；持续代理的身份、转交和恢复是独立的 P4 范围。现有 canonical 工具卡可从原参数和回执解释此次派发依据。

新调用必须符合当前 Schema；不为缺失 delegation 的新调用自动补默认理由。旧工具记录、已创建的 Task/Thread、等待和恢复仍按原事实读取，不补写或伪造过去的决策。若中断前尚未成功派发，恢复后模型使用当前 Schema 重新决策。

清理主线/嵌套模式中重复的收益规则；Schema、解析器与共享提示由工具运行时提供，原会话循环和唯一预检复用。不得为绕过新合同保留旧工具别名、宽松备用入口或基于文件数量的隐藏兜底。

## 8. 实施顺序与改动边界

1. **统一选择原则**：先修改运行时共享唤起说明及角色提示，撤下按角色、任务时长和实例数强制派发的表述。主线和获授委派能力的代理使用相同原则；Goal 的自动续跑不绑定代理数量。
2. **收紧工具入口**：工具目录提供 delegation Schema；同一解析器处理模型响应和创建前预检。输入不合格直接返回拒绝，不进入角色配置、Git 准备和注册，也不自动补造旧参数。
3. **贯通可追溯性**：原始参数、拒绝回执、成功回执和创建事件均走既有 canonical/事件入口。无需新增任务表、调度器、审批界面或预算模块。
4. **核对执行能力**：保留既有权限继承、Skill 封闭范围、深度、直接父子关系、容量、取消和 worktree 校验。purpose=user_requested 不跳过任何校验；allow_delegation 默认关闭，每层独立解释收益。
5. **验证与清理**：依次验证解析合同、真实 Schema、直接调用防绕过、主线接管、成功派发、嵌套与恢复。更新本地 Provider 夹具，删除重复短描述与过时提示；旧已完成记录按原格式读取。
6. **清除虚假完成路径**：删除基于标题/目标关键词返回固定规划与验证结论的生产入口、专用辅助函数及导出。以正常模型循环的回归替换旧捷径测试；已保存的历史结果保持原事实，尚未执行的旧任务按当前模型、权限和完成合同执行。

## 10. 当前实现边界

- `agent_delegation.rs` 提供理由解析、Schema 和共享规则。动态 developer 提示按当前 Task 和本轮真实工具重建；角色文件不另行定义派发条件。缺少 spawn、wait 或 cancel 的有效能力时不开放创建。
- `agent_spawn_preflight.rs` 校验角色、Skill、父链与深度；`task_execution_registry.rs` 在准备计划/Thread/初始消息后最后发布 Task。模型参数不构成授权凭证。
- `context_mode` 默认 fresh；显式 fork 从父 Task 当前 canonical 派发 Step 之前的合法历史边界冻结证据。运行时校验 Session、Mission、Task、Thread 与 Step 来源，调用方不能提供快照正文或替换来源。快照存在原 TaskStore 上下文包内，模型装配沿 `reference_data`，不复制隐藏思考、Provider 私有上下文、审批或资源执行权，也不进入工具重放账本。已授委派的子代理只能 fork 自己的历史；后续转交/继续仍读取同一冻结包。
- TaskStore 保存 Task/activation/转交与租约；SessionStore 保存独立 Agent Turn、Step、工具/交互。Thread 和 UI 从原事实投影。终态回调优先读取 Agent 的 canonical Task/Turn 绑定，不能由当前主线覆盖；跨主线状态事件沿 activation 定位原会话。
- `agent_service.rs` 供 HTTP/App Server 共用显式转交。读取投影不准备资源；提交必须重查来源 Turn、activation 代际和 Goal 控制版本。Web 使用服务端给出的命令及稳定 operation。
- 未转交子树受父轮生命周期约束；转交后普通停止只结算原执行范围，Session 关闭/删除结算全树，Goal 撤销只结算对应 Goal 拥有的分支。
- `context_request` 等待父任务补充时，通道开放但没有消息表示本次等待超时；任务输入关闭或会话删除则立即返回 `task_interrupted`。父任务已结束且没有已投递答复时返回 `parent_not_running`，不继续等待完整工具超时；已投递补充先交付。等待及重新准入仍沿原 TaskStore 和执行名额入口，不另存等待状态。
- 取消回执与等待共用原 Agent 结果；Task 已结束不等于资源退出，也不等于副作用未发生。插件引擎同样等待适配器/进程退出。
- Job 复用原工具 item 和 Task/Turn 身份，持久输出并按事件等待。重启后不自动重放未知副作用；问题/审批答复不自动创建新 Step。
- Skill 激活先保存原 Task/Turn 限制，再发布成功；保存失败阻止后续模型调用。主线换轮不改变代理限制归属。
- worktree 恢复沿原 Task 分配、Git 归属与新 lease 重挂接；缺失证据时拒绝从当前主线静默重建。旧 lease 清理不能释放新执行资源。
- 外部 Executor 仅预留通用接口，具体 Codex 适配器已撤下。历史外部执行证据不能满足原生工具完成合同，也不能进入 Magi 工具重放路径；本轮子代理验收只覆盖现有引擎。

主线 Continue/Restart/Archive 不能用代理 ID 绕过控制目标检查。独立代理重启后使用 `agent/continue`（HTTP 为 `/agent-runs/continue`），只接受原转交子树根和服务端投影的预期 Turn/activation，原问题或审批未处理时拒绝。同一事务接纳子树各 Task 的新 Turn，仍用原 Task/Thread、Skill 与执行副本，旧中断记录和当前主线不变。双客户端同 operation 只接纳一次，重复与重启后读取原回执；旧终态投影和恢复提交共享执行范围的 restart 锁。该入口支持可由 Magi 恢复检查点的原生执行；结果未知的副作用仍先核对，不自动重放。

可重复的验证入口见[验证文档](validation.md)。此前 16 路 `turn_harness::tests::` 回归通过 166 项，原性能基准跳过 1 项；本轮转交代理定向回归通过 12 项。真实 daemon 控制验收覆盖父轮仍运行时子代理 Turn 独立收口、SIGKILL 后直接/嵌套子树继续、原批准单次执行及双客户端幂等；Web 点击原代理继续按钮也已验收。macOS 打包 Desktop 现已验证真实 child task 卡片、详情执行结果、拒绝创建无虚构身份及两个代理的独立终态；展开前的摘要或模型最终文本不能代替这些事实。四种主对话模型的当前委派决策样本已完成，仍需更大规模重复评测及 Windows 原生进程/发行包验收；并发通过不代表已经穷尽调度交错。
