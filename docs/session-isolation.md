# 会话隔离工作副本

同一个工作区里同时跑多个会话，它们读写同一批文件：互相覆盖、变更归属混在一起，Git 分支切换还会
在别人脚下改掉文件。隔离工作副本让每个会话可以在自己的目录里读写，互不影响，确认后再合并回主工作区。
机制与 Git 无关，Git 工作区和普通目录走同一条路径。

## 模型

- **默认**：会话直接在主工作区运行，和单会话时一样，改动实时可见。
- **隔离**：会话在 Magi 管理的私有副本里运行（`<state>/session-isolations/<sessionId>/<工作区目录名>`）。
  副本是工作区的完整拷贝，会话的工具 cwd、权限根目录、终端、子代理都在副本里；主工作区原封不动。
- 两种触发方式：
  1. 用户在输入区点「隔离」（草稿会话会先落成真实会话再隔离）。
  2. 自动：提交需要工具的一轮时，发现同一工作区里另一个会话正在主工作区执行，这一轮自动改在隔离副本里
     运行（`origin = contention`，界面会说明是哪个会话占用了工作区）。切换的前置条件不满足
     （会话有未处理变更、有子代理 worktree 在用、副本建立失败）时不会失败，退回主工作区并由
     执行租约排队。
- 个人会话（没有工作区）没有可隔离的对象。

## 建立副本

`magi-session-isolation::create_isolated_copy`：

1. 优先写时复制（macOS `cp -c`，Linux `cp --reflink=always`）：整个目录秒级完成、几乎不占空间，
   `node_modules` 等大目录也包含在内且互相独立。
2. 不支持（跨卷、ext4、Windows）时退回普通复制，并把 `node_modules`、`.venv`、`venv` 以及根目录的
   `target` 改为指回主工作区的符号链接，避免复制几个 GB。
3. 不复制 `.magi`（Magi 自己的运行态属于主工作区）；`.git` 是目录时一并复制，副本里的 Git 完全独立；
   `.git` 是指向外部 gitdir 的文件（linked worktree / submodule）时不复制，否则副本会与主工作区共用
   同一份索引，此时副本里没有 Git。

## 会话怎么用副本

`ApiState.session_isolations`（`SessionIsolationRegistry`，持久化到 `session-isolations.json`，
重启后目录仍在的会话继续使用同一个副本）是唯一事实源。接入点：

| 位置 | 行为 |
|---|---|
| `dispatch_flow` / `session_continue` / 终端 | 执行根目录取副本；身份根目录仍是主工作区，策略路径由 dispatcher 投影到副本 |
| `snapshot_root_for_session` | 按「会话 + 工作区」取变更账本的入口统一把主工作区路径换成副本路径，账本以副本建立时的内容为基线 |
| `ensure_session_code_context` / `synchronize_session_changes` | 隔离会话没有主工作区的 Git 上下文，不占执行租约，不做 Git 漂移检查 |
| 文件预览（`/files/content`、`/files/raw`、定位文件） | 带会话时读副本里的版本，不带会话（工作区级）仍读主工作区 |
| 删除会话 | 回收副本目录和账本 |
| daemon 启动 | `reclaim_orphan_session_isolations`：会话已不存在的登记、目录还在但没有登记的副本（崩溃残留）一并回收，目录在后台线程里删除 |
| 输入区分支按钮、变更面板的仓库面板 | 隔离会话不显示：它们描述的是主工作区的仓库，对副本没有意义 |

子代理继承父任务的执行根目录，在同一个副本里运行；没有 Git worktree 隔离，因此沿用「同一时间只允许一个
可写代理」的规则。副本里不提供结构化 Git 工具（它们绑定的是主工作区的 Git 上下文），模型仍可用 shell。

## 合并回主工作区

副本里的改动记录在会话自己的变更账本里。合并按文件做三方比较（基线 / 主工作区 / 副本）：

| 比较 | 结论 |
|---|---|
| 主工作区内容 == 副本内容 | 已一致，只推进基线 |
| 主工作区内容 == 基线 | 主工作区没动过，直接应用 |
| 其它 | 冲突，用户逐个选择「用副本的版本」或「保留主工作区的版本」 |

- 写入以「临时文件 + 改名」完成，保留可执行位和符号链接；重命名拆成删除加新增。
- 应用成功的文件在副本账本里 `approve`，基线推进到合并后的内容，后续合并从这里继续。
  「保留主工作区」的改动仍留在副本里待处理。
- 计划（`/session/isolation/merge-plan`）只读；应用（`/session/isolation/merge`）以应用时刻的磁盘重新计算。
- 变更面板里隔离会话的「批准」就是合并：单文件批准遇到冲突返回 409，「全部批准」只合并没有冲突的文件。
- 执行过程中也允许合并，长时间运行的目标可以边做边合并；丢弃副本要求会话空闲，且副本里有未合并改动时
  必须显式确认。

## 接口

`GET /session/isolations`、`GET /session/isolation`、`POST /session/isolation/{enable,discard,merge-plan,merge}`。
状态变化通过 `session.isolation.changed` / `session.isolation.merged` 事件通知前端。

## 已知限制

- 副本里没有主工作区之外的运行环境：端口、数据库文件等全局资源仍然共用，需要用户自己协调。
- 合并以文件为单位，同一个文件两边都改过只能二选一，没有逐行合并。
- 非 Git 目录和 Git 目录体验一致；不支持写时复制的文件系统上，大项目首次建立副本会比较慢。
