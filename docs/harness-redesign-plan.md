# Magi Harness 改造计划（主线 → 子代理 → 汇报）

- 文档状态：执行中
- 来源：2026-10-04 对 harness 的派发、执行、汇报和整体结构四路审查，关键结论已回到源码核实
- 工程原则：沿用“稳定性与业务流程修复计划”的公共约定——从源头修复，不保留双链路、兼容分支和补丁式兜底；删除路径后清理调用方、协议字段和测试；每项补能复现问题的测试
- 编号：H 组按执行顺序排列；同组内的子项可以分开提交

## H1 子代理生命周期闭环

| 编号 | 问题 | 改造 | 验收 |
| --- | --- | --- | --- |
| H1-1 | 根任务失败时不级联终止子树，排队中的子代理在父任务已失败后仍被调度（`task_store.rs` 祖先检查只拦 `Pending`） | 根任务进入任一终态时统一终止整棵子树并清理执行资源；祖先链出现 `Failed`/`Killed` 时子任务不可调度 | 根任务失败后，运行中和排队中的子代理全部进入 `Killed`，不再派发 |
| H1-2 | 主模型无法主动停止跑偏的子代理 | 新增 `agent_cancel`（只能取消当前任务直接派发的代理，级联其子树并释放资源） | 取消后 `agent_wait` 返回该代理为 `killed`，资源已释放 |
| H1-3 | 父子关系有 TaskStore 和 SpawnGraph 两个事实源；SpawnGraph 生产代码从不 `mark_closed`，同一父任务累计派发第 17 个子代理时被扇出上限拒绝 | 删除 `magi-spawn-graph`，父子关系、深度和“未结束子代理数”全部从 TaskStore 实时计算 | 同一父任务顺序派发并完成 20 个子代理不被拒绝；并发未结束数超过上限才拒绝 |

## H2 子代理结果回执

| 编号 | 问题 | 改造 | 验收 |
| --- | --- | --- | --- |
| H2-1 | `agent_wait` 只在等待前取一次线程快照，子代理在等待期间完成时可能把中间过程文字当成最终结论；取“最后一条 assistant 消息”不排除带工具调用的中间消息 | 子任务进入终态时由运行时写入不可变的结构化回执（最终答复、改动、执行过的验证命令与退出码、失败原因），`agent_wait` 只读回执 | 等待期间完成的代理返回其真正的最终答复 |
| H2-2 | “声称完成”和“实际完成”无法区分 | 回执中的执行事实（改动文件、命令与退出码）由运行时从工具执行记录提取，不靠模型自述 | 回执列出子代理实际运行的 shell 命令及退出码 |
| H2-3 | 超过 12KB 的结果被通用截断压成预览；`summary` 与 `final_text` 重复；顶层 `status` 恒为 `completed` | `agent_wait` 按代理分配展示预算，去掉重复的 `summary`；顶层改为 `all_terminal` 与成功/失败计数；完整答复可通过 `context_read` 按引用读取 | 3 个代理各写 8000 字中文结论时，每个代理的结论开头都可见 |
| H2-4 | 只能等全部完成；超时结果中已终态的代理不计入“已收集” | 增加 `mode: all | any`；超时时已终态代理计入已收集 | `any` 模式在第一个代理结束时返回；超时后已完成代理不要求再次等待 |
| H2-5 | 吸收检查靠关键词匹配，未吸收/未等待的重试没有次数上限 | 删除关键词吸收检查（收集即进入模型上下文）；“仍有未结束/未收集代理”的续轮提示设次数上限，超限以明确原因结束 | 模型反复不等待时在上限内结束本轮 |

## H3 子代理工作区基线与产出合并

| 编号 | 问题 | 改造 | 验收 |
| --- | --- | --- | --- |
| H3-1 | worktree 从 `base_head` 检出，看不到主线未提交的改动 | 派发时把主线工作树（含未跟踪文件）写成临时提交（独立 index，不触碰用户的 index 和工作树），子代理从该提交检出 | 主线改完未提交就派 reviewer，reviewer 读到的是新内容 |
| H3-2 | 子代理改动不提交就只保留目录，主模型和用户都不知道改动在哪 | 子代理终态时运行时把 worktree 改动提交到代理分支；回执带分支、提交、改动文件列表 | 子代理结束后不再出现 `retained_dirty` |
| H3-3 | 没有人负责把改动合回主线 | 新增 `agent_apply`：把代理分支相对基线的改动以三方合并方式应用到主线工作树，冲突时返回冲突文件且不留半应用状态；未合并的产出在回执和前端标出 | 合并后主线工作树出现子代理改动；冲突时工作树保持原样 |
| H3-4 | 非 Git 工作区里多个可写子代理共用主目录 | 非 Git 工作区同一时间只允许一个可写子代理，预检拒绝并给出原因 | 第二个可写代理被预检拒绝 |

## H4 审批

| 编号 | 问题 | 改造 | 验收 |
| --- | --- | --- | --- |
| H4-1 | “本轮允许/拒绝”的键是 会话+轮次+工具+参数，跨代理、跨 worktree 串用 | 键加入 `task_id` 与执行根目录 | 对代理 A 的授权不放行代理 B 和主线的同参数调用 |
| H4-2 | 审批请求看不出是哪个代理发起 | 待审批项携带代理角色与标题，前端审批托盘展示 | 托盘显示“由 <角色>·<标题> 请求” |
| H4-3 | 子代理等审批时主模型直到 `agent_wait` 超时才知道 | 子代理进入等审批时向父任务推 `attention_required` 信号 | 子代理请求审批后，父任务的 `agent_wait` 立即返回 `attention_required` |
| H4-4 | 审批等待有两套实现，判断“轮次是否仍有效”的标准不同 | 合并为一套 | 只剩一个审批等待实现 |

## H5 容量与准入

| 编号 | 问题 | 改造 | 验收 |
| --- | --- | --- | --- |
| H5-1 | 预检只看容量不占槽位，同轮多次派发都返回 `started`；coordinator 在 `agent_wait` 中仍占槽位 | `agent_spawn` 结果的 started/queued 以真实准入为准；coordinator 等待子代理期间让出槽位 | 2 核机器上并行派发 2 个代理都能运行 |
| H5-2 | 提示词中的容量说法自相矛盾，引用不存在的字段 | 容量事实只有一处，提示词由它渲染 | 提示词与运行时上限一致 |

## H6 派发合同与角色

| 编号 | 问题 | 改造 | 验收 |
| --- | --- | --- | --- |
| H6-1 | 提示词写死 5 个内置角色，自定义角色不可见；角色填错的报错不列可用角色 | 由角色注册表动态生成可派发角色摘要；报错附可用角色 | 新建自定义角色后 coordinator 提示词中出现该角色 |
| H6-2 | 省略 `capabilities` 时注入全部能力正文（约 15KB），与目录描述冲突 | 省略时只激活角色声明的默认能力子集；统一一处描述 | 省略时系统提示不含全部能力正文 |
| H6-3 | reviewer/explorer 的“只读”只是提示词 | 角色声明写入权限；只读角色不暴露写类工具，使用只读执行根 | explorer 调用 `file_write` 被拒绝 |
| H6-4 | 子代理拿不到用户原话；`references` 只校验格式；父任务 Skill 被原样继承 | 回执外的 brief 附带本轮用户原始请求；预检校验引用存在；Skill 不继承，由 `agent_spawn` 显式指定 | 坏引用在预检被拒绝；子代理不继承父 Skill |
| H6-5 | `task_kind` 无实际作用；提示词提到 spawn 不会返回的 `degraded`；不可修复的错误让模型“刷新配置” | 删除 `task_kind`；修正提示词；错误回执加 `retryable`，不可修复时指引由主线完成 | 协议与提示词一致 |
| H6-6 | 对排队中的子代理 `agent_send` 直接失败 | 排队中的子代理接收消息，开始执行时读取 | 排队期间发送的补充上下文在子代理首轮可见 |
| H6-7 | 单个子代理只受全局 200 轮上限约束；子代理 token 不计入 Goal 预算 | 子代理有独立轮数上限；token 计入其根任务所属 Goal 预算 | 子代理超过自身上限时以明确原因失败 |

## H7 入口路由去关键词

| 编号 | 问题 | 改造 | 验收 |
| --- | --- | --- | --- |
| H7-1 | 路由、协作模式、必调工具链、强制工具都由用户文本子串匹配决定；“读 AGENTS.md”“HTTP 代理”被强制派发子代理；默认走无工具 Chat，违反架构文档“无法确定时选 task” | 路由只看结构化输入：会话命令、GPT Web 引擎、引导、目标模式开关、技能、中断续做；其余工作区会话一律进入带工具的主线，是否用工具/派发代理由模型决定；删除 `CollaborationMode` 及关键词词表 | “读一下 AGENTS.md”走带工具主线且不强制派发；“为什么报错”能读代码 |
| H7-2 | 对话循环（`session_turn_execution.rs`）与任务循环（`conversation_loop.rs`）重复实现工具执行、重试、账本、上限、压缩；生产中对话循环固定 `use_tools: false` | 对话循环收敛为无工具的流式回复，删除其中的工具、引导、必调工具链等分支和第二个工具批执行器 | 对话循环不再引用工具执行器 |

## H9 重启恢复

| 编号 | 问题 | 改造 | 验收 |
| --- | --- | --- | --- |
| H9-1 | worktree “占用中”标记原样恢复，启动时不核对，主线 Git 写操作可能被永久拒绝 | 启动时按 TaskStore 中仍在运行的任务核对占用，释放失效占用 | 重启后主线 Git 写操作不再被已失效的子代理占用阻塞 |
