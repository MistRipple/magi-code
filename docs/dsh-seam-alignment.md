# DSH 对齐：Magi 插件系统的当前设计

> 状态：里程碑改造的权威设计，2026-11-17 修订（第二版：取消翻译层，以 DSH 插件合约为 Magi 唯一插件接口）。**本文取代此前的插件设计文档**（`plugin-system-requirements-design.md` 及其附属的剪除审核、交付记录），旧文档已过时，不再修改，仅作历史。现行作者指南与内部控制分别见 [DSH 原包作者指南](dsh-plugin-authoring.md)及[共享宿主协议](plugin-host-protocol.md)。
>
> 本文不代表任何一项已交付。依据：DSH 仓库 `docs/capability-seams.md` 的全部 113 个 `ctx.*` 服务与 `docs/architecture.md`（master，2026-11-17 读取，不锁版本）；Magi 源码；对 100 个真实 DSH 插件的静态扫描（第 5 节）。表中分类是文档与名称层面的判断，不是逐项代码审计。

## 1. 决策（用户）

1. **Magi 的插件接口按 DSH 对齐：DSH 支持的，Magi 同样支持。** DSH 对插件放行的事项（审批决策、系统提示整体改写、模型请求拦截、替换执行循环和会话存储后端等），Magi 不另设例外。先做哪个，只由实际依赖决定（第 10 节）。
2. **会话能力组合与 DSH 一致。** 插件按应用全局安装与启停；会话启用哪些能力，由预设从已启用插件中组合。
3. **跟随 DSH 上游演进，不停在旧版本。** 开发线跟随 DSH master，上游更新后重新读取接缝清单核对本表；每次 Magi 发布锁定具体的 DSH SDK 版本、依赖摘要与能力基线，生产环境不跟随浮动版本（第 3.4 节）。
4. **Magi 内核实现保持自有，只在对外接口上对齐 DSH 的接缝。** 不要安装期翻译与改写这类中间层：安装只做校验与放置，运行在单层宿主里。
5. **旧设计文档不再修改。** 本文是替代。
6. **插件管理页的槽位（`plugins.*`）渲染在该插件自己的设置页里，沿现状。** 设置页本来就是槽位的承载位置（导航入口加原生页头，正文由插件的组件渲染）；不新增界面位置，也不另做分区设计，也不做 DSH 式的插件管理界面。
7. **界面范围只做到设置页、主页面和右栏标签页。** 主对话（输入区、对话区、工具调用视图、会话头部）、左栏、外壳浮层的槽位暂不支持，先把核心接缝对齐，后续有条件再评估。这些位置的设计想法保留在第 8 节末尾作为起点。
8. **范围外的界面槽位不再拒绝安装，而是允许安装并明示缺失。** 安装预览展示支持范围并标明“激活后检查”；激活后插件详情依据真实注册列出“N 项界面功能在 Magi 中不可用”及具体槽位。其余功能按自身合同运行。见 8.4。
9. **目标架构采用本方案，补强的是执行合同与交付分期，不是退回旧插件边界。** daemon 仍是唯一内核，但可以与可替换实现共存：daemon 负责选择提供方、绑定调用身份、管理生命周期、提交事实；插件可以承担实际策略或执行实现（第 3 节）。
10. **DSH 插件合约是 Magi 唯一的对外插件接口。** 包格式（npm 包、`package.json` 的 `exports` 与 `./client`）、后端 `ctx.*` 服务与事件、客户端槽位与标准套件，都以 DSH 为准。Magi 现有的 SDK 2（清单加 `api.*`）降为 Node 插件宿主与 daemon 之间的内部协议，不再作为公开插件接口，不再接受按它编写的第三方包。核对：官方插件中心目录为空，`examples/plugins` 只有说明文字，没有需要迁移的 SDK 2 插件。
11. **从产品长远架构出发，不做兼容，不打补丁。** 不建翻译层、垫片、别名、“部分实现”或“最小外观”；Magi 缺的事实与能力在内核里正式补齐，做不到的明确不提供。
12. **所有已启用插件运行在同一个 Cordis 宿主进程中**，与 DSH 一致，插件之间可以提供和注入服务。单个插件的启动失败由 Cordis 隔离；进程崩溃时整体重启，进行中的调用按 3.1“撤权与停用”处理。接受的代价：一个插件让进程崩溃会影响全部插件。
13. **建设正式的配置组合与加载能力**（2026-11-17 用户确认）。原包可通过 `loader` 读取与管理真实加载图，配置来源、提交修订、依赖解析、激活与回收属于同一产品能力，由 daemon 的插件管理领域拥有。必须覆盖真实文件配置的读取与变更接纳，不能以虚构 include 行、profile 目录投影、文件调用拦截或忽略依赖让原包启动。`pluginManager` 的安装、启停与升级沿同一所有者；`hmr`、`profileContext` 按其实际公共合同设计，不能沿用旧模拟实现或仅为单包造外观。具体合同见 3.7。
14. **插件配置以 daemon 接纳的配置修订（CAS）为唯一生效事实**，宿主据此向 Cordis 插件传入配置。设置页、程序化加载编辑与文件配置变更沿同一接纳与提交机制；配置文件是正式编辑来源，运行图是已接纳修订的投影，不另存可独立生效的第二份配置。不迁移旧安装物与旧模拟 profile 数据。
15. **硬切换，不迁移。** SDK 2 包与旧翻译安装物不迁移、不加载；切换后显示为“需要重新安装”，用户重新安装 DSH 原包（第 3.4 节）。

## 2. 对齐原则与“完全运行”的定义

- **完全运行** = 只使用 DSH 公开合约的插件，其用户目标在 Magi 中完整可用。范围按决策 7：后端接缝加设置页、主页面、右栏标签页；主对话与左栏等位置的界面功能暂不计入，也不声称支持。
- **没有翻译层。** DSH 原包直接安装、直接运行。安装期不扫描、不试跑、不合成清单或权限、不改写代码；能否运行由运行时决定，而不是由一张规则表预判（第 3.4 节）。
- **验收以真实业务为准。** 固定原包与版本，在真实 Electron 与 daemon 中完成业务任务（第 10 节）；静态扫描结果只作历史需求分布参考，激活成功数只作辅助指标。
- **服务只有两种状态：完整实现或不提供。** Node 插件宿主提供的每个 `ctx.*` 服务、事件和标准套件 hook，要么按 DSH 合约完整实现（背后是 daemon 的正式能力），要么不提供。不提供时沿 DSH 自己的语义：可选注入的分支不运行，必需依赖缺失则该插件启动失败并明确说明缺哪个服务。不做“部分实现”“最小外观”“调用时报未提供”的半成品。
- **缺事实就补内核，不在宿主编造。** DSH 合约需要而 Magi 没有的事实（例如事件序号、条目所属的模型步骤、轮次结束原因），作为 Magi 自己的领域事实在内核里补齐，命名不带 DSH；Node 宿主只做格式表达，不合成、不猜测、不填占位值。
- 接口对齐分三层：签名；语义（顺序、`next` 环绕、错误、取消、时机）；对象身份。前两层对齐。**对象身份无法跨进程共享**，由第 3.2 节的句柄与“对象行为清单”承担：清单里的行为统一实现，清单之外的对象修改在注册时明确拒绝，不做逐插件的特殊处理。
- 给 DSH 宿主安装文件打补丁的功能（如 dsh-purge 的 86 条宿主补丁）在 Magi 中没有宿主可打，标“不适用”，不显示为失败。
- DSH 专属名字与逻辑只放在 Node 插件宿主，Rust 内核不出现 DSH 分支（现有的 DSH 版本豁免、兼容投影等随平台重构删除，第 3.4 节）。
- 按真实任务形成少数几项公共能力，不把 DSH 的每个服务名机械对应成一个新的 Rust 服务（第 7 节）。
- **架构适配的实施边界。** 新能力必须落在正式领域服务、Node 宿主的 DSH 合约实现或统一页面宿主中，由同一事实源与生命周期管理。RPC 编解码、句柄和事件表达是这些公共合同的组成部分；不得借此保留旧 SDK 包执行入口、profile 模拟、按包名或版本分叉、假服务、源码改写或失败后调用旧实现。原生提供方的故障处理仅按第 3 节的正式合同执行，不作为旧路径兜底。每阶段验收同时核对旧入口及其消费者已经清退；本设计不声明尚未实施的代码清理已经完成。


## 3. 执行合同

本节是对“接口对齐”落地方式的约束：daemon 仍是唯一内核，插件可以提供实际策略或执行实现。需要明确的是提供方如何被选择、如何组合、失败和撤权时怎么办，以及跨进程后同步返回、流、`next()` 环绕、对象句柄分别怎么工作。**3.1 到 3.3 的运行时合同已按 3.5 确认。DSH 接缝的正常调用语义以上游实际行为为准；本文明确规定的跨进程故障合同（包括 Q3）是 Magi 的正式产品行为，不能被“以上游为准”隐式覆盖。落地时逐项核对，新增差异须更新公共合同，不能添加逐插件兼容分支。**

### 3.1 提供方合同

**依据：DSH 的实际语义（已核对其工具执行管线、审批接缝与预设注册文档），不是自拟规则。** 每个可替换接缝按下列四项定义，缺一项不得开放。

**基数与选择。**

| 类型 | DSH 语义 | 例子 |
| --- | --- | --- |
| 环绕链（waterfall） | 监听器收到 `(参数, next)`，调用 `next()` 委托下游，不调用则短路；按注册顺序，可用 `prepend` 排到最前；最终值由最外层返回 | `tools/pre-execute`、`tools/execute`、`tools/post-execute`、`system-prompt/assemble`、`agent/pre-step`、`llm/stream` |
| 单终端回答者 | 一个部署只有一个终端回答者，其余监听器只能委托；兄弟顺序不是优先级机制 | `approval/request` |
| 单调守卫 | 在 pre-execute 链之后同步运行，只能拒绝；后来的监听器不能把拒绝改回放行；所有者的不可绕过策略注册为守卫，身份受保护 | `ctx.tools.guard` |
| 单提供方 | 一个后端 | `sessionPersistence`、`llm` 适配器注册、压缩后端 |
| 扇出观察 | 所有监听器并行观察，无返回值 | `session/event`、`turn/end` |

Magi 默认提供方是原生实现；插件的贡献作为候选随插件全局启用，单提供方和单终端回答者由用户设置选定。

**合成与审批（沿 DSH）。** 工具调用先过 `tools/pre-execute` 链，链上的决定是放行、拒绝或询问；询问交给唯一的终端回答者；之后才是单调守卫。

- **守卫是 daemon 的最终守卫。** Magi 现有的硬拦截规则（`hard_block`，如强推历史、破坏性命令）对应为 Magi 注册的单调守卫。**插件的放行只表示“插件自身没有阻止”，不能绕过 Magi 的硬规则。守卫必须在所有可改写参数的环节完成之后，对最终参数重新校验**，这样插件不能通过 pre-execute 改写参数来规避硬拦截。守卫失败、超时、宿主缺失或协议错误，一律拒绝。（Q1）
- **审批终端只有一个。** 默认是 Magi 原生审批界面；用户可以显式选择某个插件作为终端回答者，其余插件只能观察或委托。选择结果按提供方版本持久化；已有审批不会因设置变化被另一个回答者接管；选定的插件崩溃、超时或返回非法结果时，按 `unavailable` 拒绝，**不能因为插件回答者不可用而静默切回 Magi 原生审批**，否则会改变用户已经选择的安全策略。（Q2）
- 审批策略沿 DSH 的两档（`ask`、`never`；`never` 直接拒绝，不询问），Magi 现有的 Restricted 与 FullAccess 访问档位对应 DSH 的权限预设。审批与放行的事实始终由 daemon 记录，并标注决定来自哪个提供方。

**失败。**
- **门类链**（审批、pre-execute、守卫）：没有回答者、回答者失败、超时或非法返回，一律拒绝（fail closed）；链里任一环抛错，该工具调用记为错误结果，不执行（沿 DSH 管线归一化）。新宿主的相关接缝在工具管线与提供方端口阶段分别验收。
- **转换类链**（提示装配、模型请求环绕、步骤前环绕）：插件崩溃或超时，按**下游状态**细分，**不能一概“继续”**（Q3）：
  1. 尚未调用下游：跳过该插件，继续用当前候选值；
  2. 已调用下游且已有结果：使用该下游结果，**不重复调用**；
  3. 下游调用已开始但没有可复用结果：把本次调用标记为**结果未确定**，不自动重放，不伪造原生结果。
  
  所有情况都记录结构化告警和插件健康状态。`llm/stream` 可能已经发出真实模型请求，模型环绕必须记录是否已调用 `next` 以及下游是否已有结果，避免重复请求、计费或副作用。

**流式与环绕调用的实现合同（Q3 落地）。** 每次进入环绕链，daemon 为整条链建立一条调用记录，至少包含：调用 ID、插件与激活代次、是否已调用下游 `next()`、下游流是否已开始、下游是否完整结束、是否已产生用量。插件失败或超时后，按记录决定结果：

| 记录状态 | 结果 |
| --- | --- |
| 尚未调用下游 | 跳过该插件，用当前候选值继续 |
| 下游已完整结束 | 复用下游结果，不再调用一次 |
| 下游已开始、未完整结束 | 本次调用标记“结果未确定”；不重放、不伪造原生结果；已产生的用量照实记账 |

纯转换（提示装配、步骤前处理）不调用模型，失败只适用第一行。三种情况都写入结构化告警与插件健康状态。

**候选与冲突。**
- **候选**：已启用插件在运行时注册某个接缝的提供方，即成为候选，身份是 `<种类>:<插件 id>:<贡献 id>`（3.3）。同一插件对同一身份重复注册，后一次注册失败并报告给该插件。
- **按类型参与**：环绕链、守卫、扇出观察，所有已启用插件的注册都参与，按 Q4 的顺序；单提供方与审批终端只用被选定的一个，其余候选空闲。
- **选择与绑定**：单提供方与审批终端的选定写在预设里，会话创建时随预设修订绑定（3.3）；预设未指定时使用 Magi 原生实现，不按注册先后自动选择。
- **升级**：插件升级产生新的提供方版本。数据与执行类单提供方（存储、压缩、执行循环等）按身份延续选择；审批终端按 Q2 绑定提供方版本，升级后需要用户重新确认，确认前按 `unavailable` 拒绝并提示原因。
- **不可用时的最终结果**：

| 类型 | 选定或参与的插件不可用时 |
| --- | --- |
| 转换类环绕链、可选提供方 | 下一个决策边界回落 Magi 原生实现，并向用户展示回落事实 |
| 单调守卫 | 拒绝 |
| 审批终端 | 按 `unavailable` 拒绝，不切回原生审批 |
| 数据后端单提供方（如 `sessionPersistence`） | 该后端上的会话无法打开，明确报错，不改用其他后端（第 9 节） |
| 扇出观察 | 该插件不再收到事件，其余照常 |

**撤权与停用。**（Q5）插件停用、卸载或崩溃后，**立即停止接收新的调用**；正在进行的调用按其合同排空、取消或标记为结果未确定。到下一个决策边界（下一次审批、下一步模型请求、下一次提交）：转换类和可选提供方回落到 Magi 原生实现，并向用户展示回落事实；**硬守卫仍然拒绝；选定的审批终端不可用仍按 `unavailable` 拒绝，不静默更换回答者**。插件可用性变化影响已有会话的后续决策边界，但**不能修改已经提交的历史事实**。

### 3.2 运行时语义（跨进程后怎么工作）

Node 插件宿主原生实现 DSH 合约，由四个部件组成：**服务实现**（`ctx.*` 服务调用 daemon 的正式能力）、**事件桥**、**页面宿主**（客户端槽位与标准套件）、**依赖解析**。DSH 专属语义只在这一层，Rust 只提供正式业务能力。

| 语义 | 承载方式 |
| --- | --- |
| 同步返回 | 宿主持有 daemon 推送的只读快照，同步读取读快照。**快照 revision 单调递增；任何需要当前权威事实的写入或裁决都必须异步重新读取并校验 revision。** 需要同步写语义的调用，按调用类别逐类处理，不承诺一律由快照满足 |
| 流 | 事件桥承载，有界队列，背压，取消随调用租约传播 |
| `next()` 环绕 | 瀑布链在 Node 宿主内运行。daemon 在定义好的点（步骤前、提示装配、模型请求与流、工具执行）调用宿主一次，宿主跑完整条链；链里调用 `next()` 触达原生部分时，经双向调用回到 daemon 执行（例如 `llm/stream` 里调用 `next()` 即由 daemon 发出一次模型请求，调用两次就发两次）。daemon 为整条链设置 deadline，链上任意环失败按 3.1 处理 |
| 对象句柄 | 插件拿到的是句柄：`(类型, id, revision, 实例代次)`，不是内核活对象，也不能依赖跨调用的对象引用。**实例代次**在插件进程重启、插件升级、重新启用后变化，此前签发的句柄全部失效；不能只靠可能重新从 0 开始的 revision 判断 |

**宿主传输原语与对象业务行为要分开**（Q6）：
- **传输原语**：读取属性（来自快照）、订阅事件、调用公开服务。这是宿主与插件之间的通道，不代表对象的某个方法被开放。
- **对象业务行为**：插件对内核对象“做事”的能力，**必须逐项登记，不能因为存在通用调用通道就自动开放**。v1 只开放一项：**命名转换端口“消息投影转换”**，替代“给实例的方法打补丁”（来源：dsh-purge 对会话 `deriveMessages` 的回退过滤）。新增条目必须对应一项通用能力，而不是一个插件。

不在清单内的做法（给对象写属性、替换任意方法、持有对象长期引用并依赖其内部状态）：注册时明确拒绝并说明，计入缺失说明。

### 3.3 能力组合最小合同

**依据：DSH 预设注册表的语义。** DSH 的预设是声明式的：“通过预设选择一个 Agent 的工具、提示段和技能”；预设定义是普通的插件行（`plugins: [...]`），更新或删除一个定义会使旧修订退役，**已有 Agent 继续使用它已绑定的组合**，新会话取用户默认预设。

“插件全局安装启停，会话通过预设组合能力”会影响工具目录、提示构建、事件分发和提供方选择，所以基础合同先于具体接缝确定。最小合同五项：

1. **能力身份**：`<种类>:<插件 id>:<贡献 id>`，跨版本稳定；种类包括工具、技能、提示段、提供方。
2. **提供方选择**：同 3.1；预设是“启用哪些工具、提示段、技能，选定哪些提供方”的一份声明。
3. **组合顺序**（Q4）：按 **daemon 持久化的插件激活序号**形成稳定顺序，**不是 Node 进程某次启动的加载顺序**；同一插件内按声明顺序；`prepend` 只影响同一接缝内的确定性排序。这样重启、在线升级和并发激活不会改变链路顺序。当前不提供用户调序入口，留到后续。
4. **会话绑定**：会话在创建时绑定预设的一个修订，由 daemon 保存为会话事实；该会话的工具目录、提示构建、事件分发都以这份修订为准；会话恢复时使用其绑定的修订。
5. **生效时机，分两类**（Q5）：
   - **组合变更**（编辑预设、改默认预设）：只影响新会话，已有会话保留已绑定的修订，沿 DSH；
   - **可用性变化**（插件停用、卸载、崩溃）：影响已有会话的后续决策边界，规则见 3.1“撤权与停用”：立即停止新调用，到下一个决策边界回落，硬守卫与选定审批终端不可用时仍拒绝，不改写已提交历史。已绑定的修订引用了不可用的插件时，会话照常使用其余部分，并向用户展示缺失。

预设的编辑界面可以后做，不需要先建设庞大的通用框架。

### 3.4 插件平台结构（取代安装期翻译）

**安装。** 来源是 npm 包（或用户给的包文件）。daemon 拥有安装、启停、升级、卸载的唯一事实；安装只做四件事：解析并锁定依赖（DSH SDK 包由 Magi 随发行提供同一份，原包其余依赖按其 `package.json` 安装）、校验包结构与入口、放置到 Magi 的插件目录、向用户展示安装确认。授权沿 DSH：插件以用户权限完全受信运行，用户在安装时确认。**不做**：静态扫描与兼容结论、受限试跑、合成清单与权限、包装入口、改写客户端代码、按扫描结果拒绝安装。

**贡献全部在运行时注册。** 工具、命令、技能、模型数据源、设置结构、路由、槽位组件、事件订阅，都由插件在 `apply` 中注册，经 daemon 的运行期目录进入产品；停用、撤权、崩溃时随实例回收（已有运行期目录与租约机制沿用）。观察类事件已是按需订阅（第 10 节第 2 项）。

**版本与发布。** 开发线跟随 DSH master（决策 3）；每次 Magi 发布锁定 DSH 上游提交、SDK 精确版本、依赖锁定文件摘要和能力基线（提供的服务、事件、槽位与标准套件清单），随发行版提供，生产环境不跟随浮动版本。版本声明沿该基线的 DSH 正式规则：`engines.dsh` 存在时按其范围校验宿主版本，否则检查 DSH SDK 的 `peerDependencies`；两者同时存在时不另造取交集规则。声明格式无效或有效范围不接受宿主版本时明确失败；未声明版本要求的情况同样按上游规则处理，不能推断为完整支持。预览、安装、更新与激活共用同一判定，不设版本豁免、包名例外或失败后切换其他 SDK。跟随上游变更时同步更新这份正式规则及回归，不能保留第二套解释路径。

**硬切换（决策 15）。** SDK 2 包和旧翻译安装物不迁移、不加载。平台切换后，它们在插件列表中显示为“需要重新安装”，并提供重新安装原包的入口；不当作普通运行错误，也不尝试启动。

**安装预览。** 安装前不运行原包，因此只展示能确定的信息：包的元数据与入口、对 DSH SDK 的版本要求、本次发布的能力基线。服务、槽位等都是运行时注册，预览中标为“激活后检查”。激活后依据真实注册结果，在插件详情中列出缺失的服务与范围外槽位；之后动态新增的注册同样更新详情。

**切换方式。** 在开发线上完成新宿主与所需公共能力，第 10 节第 1 阶段验收通过时一次性切换并删除旧路径。开发过程不建立新旧互调、运行时路由开关或失败回旧实现；新宿主独立完成固定原包验收，不以旧路径补足功能。切换前的源码现状不构成保留旧实现的产品承诺，不发布新旧双轨。

**插件宿主进程（决策 12）。** 所有已启用插件运行在同一个 Cordis 树里，插件之间可以互相提供和注入服务；取代现在的一插件一宿主进程。Cordis 负责单个插件的启动失败隔离；进程崩溃时整体重启，进行中的调用按 3.1“撤权与停用”处理。实例代次（3.2）随宿主进程重启变化。**插件配置**由 Magi 插件设置提供（决策 14）。

**删除清单。** 平台重构完成时一并删除，不保留双份：
- 安装期：`scripts/compat/core` 的扫描、规则、报告、能力清单，`scripts/compat/dsh` 的规则表与翻译器，`scripts/compat/install` 的准备、记录器、客户端分析与改写、槽位记录；
- 运行时垫片：按 SDK 2 `api.*` 转接的 `dsh-host.mjs` 结构、`nullableEvents` 协商、DSH profile 目录模拟（`profile*.mjs`、`DSH_HOME` 重定向）；其中仍需要的服务按“完整实现或不提供”在新宿主中重写；
- Rust：插件系统中的 DSH 版本豁免策略（`lifecycle/compatibility.rs`）、翻译运行时状态与 `PluginDshCompatibilityProjection` 等兼容投影、对 `extension/compat.json` 的读取；
- 文档：第 5 节只保留为历史需求分布；扫描结论不作为任何阶段的依据。

**验收。** 以固定原包的真实业务任务验收，见第 10 节；激活成功数只作辅助指标。

### 3.6 共享宿主的故障边界（决策 12 的落地）

- **插件级失败与进程级故障。** 宿主在 Cordis 管理的激活和调用边界捕获异常：`apply` 或注册校验失败时，释放该次激活的资源、撤销贡献并报告插件启动失败；缺失必需服务按 Cordis 注入合同进入明确的等待或失败状态，不提交为运行成功。共享服务依赖按下述规则解除。运行期工具、路由和事件处理异常按对应接缝结算，普通业务错误不触发整个宿主重启。未捕获异常、无法完成清理、进程退出、事件循环卡死或超出宿主资源边界属于进程级故障，失效整个宿主代次后按重启合同处理。Cordis 的 effect 清理不等于 OS 沙箱，不能保证回滚插件自行产生的外部副作用。以上均须用实际激活失败、调用异常与进程崩溃验收，不把框架能力当成交付证据。
- **两种代次。** 宿主进程代次：每次启动宿主进程加一。插件激活代次：插件每次激活加一（启用、升级、重新启用、宿主重启后重新激活）。daemon 签发的调用、句柄与贡献都带这两个代次。
- **旧响应与旧句柄失效。** 宿主进程退出时，daemon 把该代次的全部进行中调用按 3.1 结算（未开始的失败，已开始的按 Q3 记录处理），之后收到的旧代次响应一律丢弃；旧代次签发的句柄与运行期贡献全部撤销。插件激活代次变化时，同样只撤销该插件的部分。
- **共享服务的提供者停用。** 沿 Cordis 语义：提供服务的插件停用后服务被移除，必需注入它的插件被挂起，可选注入的分支卸载；服务重新出现时恢复。被挂起的插件在详情中显示“等待服务 X（由插件 Y 提供）”，其运行期贡献随挂起撤销。
- **连续崩溃。** 宿主崩溃后自动重启，退避递增；5 分钟内崩溃 3 次（初始阈值，按验收调整）即停止自动重启，插件页显示“插件宿主已停止”，并列出崩溃时进行中的调用及其所属插件、最近启用或更新过的插件，用户可停用其中任意插件后手动重启。若崩溃发生在某个插件的激活过程中，该插件自动停用，并记录原因。
- **资源保护。** 能保证的：每个插件的调用与事件队列有界、每次调用有截止时间、超出即按 3.1 失败；daemon 定期探测宿主，宿主事件循环无响应超过阈值即视为崩溃并重启，内存超过上限同样导致重启。**做不到的**：同一进程内无法抢占单个插件的 CPU 或限制它的内存，这是决策 12 接受的代价；故障归属依据探测失败时的进行中调用记录。


### 3.7 配置组合与正式加载（决策 13–14）

**真实任务与证据。** 固定原包 `dsh-plugin-mgr@0.2.13` 的 `dist/index.js` 必需注入 `webServer` 与 `loader`；`dist/http-q4G0rVPe.js` 通过真实 include 入口定位 `cordis.yml`，读取相邻的 `package.json` 与 `cordis.patch.yml`，并直接写入后者表达启停意愿。仅提供 `pluginManager` 无法满足这份原包合同。用户选择建设通用加载能力，样本仍属于必过任务，不改包、不删必需依赖、不缩小验收范围。

**唯一所有者与提交。** 在 daemon 的插件管理领域演进安装与加载模型，记录配置来源、内容摘要、期望修订及已接纳修订。设置 CAS、加载服务编辑和文件编辑进入同一配置接纳事务，完成结构、包来源、目录与身份校验后才提交可执行修订；Node 只实现 DSH 加载语义并运行已接纳的图。文件编辑表示候选配置已保存，不代表插件已运行；生效、等待服务、失败及恢复以 daemon 的提交和运行事实为准。语法错误或冲突要显示实际原因与未接纳来源，不能制造成功或用双向同步覆盖另一编辑者的内容。读取文件的原包可以看到编辑意愿，Magi 原生管理界面必须同时表达接纳与生效状态。

**真实配置来源。** 实现 DSH 配置文档的真实结构、稳定行身份、包依赖与 include/配置层组合语义；不生成仅供某插件读取、却不参与正式加载的假文件。安装清单、依赖锁、配置文档与已接纳图须注明各自拥有的事实及提交关系。提供给原包的 `loader.entries()`、`resolve()` 等返回实际注册和加载条目，服务增删使用 Cordis 自身的注入与 effect 生命周期。安装、启停、配置编辑、重启恢复复用同一图收敛入口；不存在原生管理和第三方管理各自激活插件的路径。

原包可直接编辑的加载项目（`package.json`、依赖锁、`cordis.yml`、`cordis.patch.yml` 及包管理器产生的安装内容）是**真实的候选来源**，不是当前可执行安装物。Mgr 自行运行包管理器也进入这份来源；daemon 验证后提交新安装／配置修订，执行不可变的已接纳包和共享 SDK。这样原包自身更新不会原地覆盖正在执行的模块，也不会把原包“文件已保存”的回执变成 Magi 的“升级已完成”。Magi 原生安装与设置编辑同样进入该来源和接纳入口；来源内容与已生效修订不一致时必须显示待接纳或具体失败，不以后台双向同步消除差异。

**文件编辑与恢复。** 文件监听是正式配置来源的变更通知，必须结合内容摘要与修订校验，不能依赖固定等待后假称已生效。变更接纳失败保留文件和诊断；已接纳修订及待处理变更可追踪。重复通知不得重复启动，停用和卸载须先失效旧调用；恢复不重放插件业务副作用。DSH 的 `flush`、配置保存回执与原包的“写文件后异步生效”语义分别按实际合同呈现，不把文件写入回执冒充运行成功。

**接纳必须早于执行。** 已核对上游 `Loader`／`EntryTree`：`create/update/remove` 及 Fiber 保存的 `commit(change)` 是树内修改后的通知；官方 `Include` 也会读取文件并直接更新运行树。因此不能直接启用这两者的自动加载，再把 `commit` 接到 daemon 当成唯一提交。Magi 的正式加载实现须将来源编辑作为候选，经 daemon 接纳后才运行；读取条目返回该真实图，运行中注册与 effect 仍使用 Cordis。源文本解析、静态图准备和修订接纳不等于 `ctx.loader` 已提供。所需编辑与同步方法的完整合同必须一起实现后才能注册该服务。

## 4. 处置分类

| 处置 | 含义 |
| --- | --- |
| 已有能力 | Magi 内核已有对应的正式能力；Node 插件宿主按 DSH 合约完整实现该服务即可 |
| 补端口 | Magi 内部有该能力，要新增或放宽对插件的端口，必要时补齐领域事实 |
| 新建 | Magi 没有对应能力，需先设计 |
| 宿主服务 | DSH 的宿主、客户端或 API 外壳服务；对应 Magi 自有的产品服务。要么经 DSH 合约完整提供，要么不提供（依赖它的插件按 DSH 语义降级或启动失败），不做“最小外观” |
| 不提供 | 遥测、账号、实验、调试类；DSH 插件自身以可选注入使用，Magi 不提供，插件按 DSH 语义自行跳过 |

## 5. 需求分布（历史静态扫描，仅作参考）

> 本节数据来自旧翻译层的静态扫描器（属于第 3.4 节的删除清单），只用来说明插件生态的需求分布、决定先做什么；不作为能否运行或验收的依据。“阻塞”“已接通”等说法指旧扫描器的判定，不是产品状态。

**方法。** 历史记录取 npm 上关键字 `dsh-plugin` 搜索结果前 100 个包（2026-11-17），记录排除 4 个 PDF 原生二进制子包、下载解压 95 个包；原记录尚有 1 个包去向未说明，不补算为成功或失败。下载使用 `npm pack --ignore-scripts`，不执行包代码，由旧 `scripts/compat` 静态扫描器分析。**该扫描器属于第 3.4 节的删除清单；这里的数字只说明历史需求分布，新的验收使用第 10 节单独锁定的原包与业务任务证据。**

**覆盖。** 95 个中 79 个被旧扫描器识别为 DSH 插件并完成扫描；16 个不是插件（目录、命令行工具、规范文档）或没有可扫描源码。历史后端分类中，50 个未记录阻塞，29 个记录了阻塞；再叠加旧界面规则，43 个未记录阻塞（54%，见第 8 节历史统计）。**这些数值仅反映旧规则的判定，不代表当前安装准入、激活结果、业务支持率或整个生态；新平台不得以复刻旧规则作为实现目标。**

**后端依赖：使用最多的服务**（使用该服务的插件数，79 个中）：`tools` 34，`webServer` 28，`settings` 14，`commands` 14，`connection` 14，`llm` 9，`skills` 9，`credentials` 9，`agents` 8，`sessions` 6，`pluginManager` 5，`systemPrompt` 4，`storageDomain` 4，`workspaceRegistry` 4。使用事件最多的是 `session/event` 7、`agent/created` 5、`agent/pre-step` 3、`tools/pre-execute` 3；`system-prompt/assemble` 仅 1 个，`llm/stream` 在该样本中为 0。

**29 个被阻塞的原因**（受影响插件数）：`session/event` 逐条事件 6；`ctx.agents` 5；`skills.registerProvider`（含 `dsh-skill` 导入）5；`dsh-session` 导入 4；`agent/pre-step` 3；`agent/created` 3；`storageDomain` 3；`tools.guard` 3；`credentials` 约 3；`sessionQuery` 2；`tools/result`、`pre-execute`、`post-execute` 各 2；`workspaceRegistry` 2。

**结论。**
- 历史样本主要依赖工具、页面路由、设置、命令。新宿主按 DSH 合约复用 Magi 正式领域能力，缺失部分在所属层补齐；旧扫描器记录的接通状态不能作为当前产品可用证明。
- 阻塞集中在**读取会话与 Agent、会话与 Agent 事件、工具执行管线事件、技能提供方、凭据、存储域**。这些都是“补端口”或“新建”，而且以只读或观察为主。
- **要求替换执行循环或会话存储的插件，在样本里没有出现**（`agentLoop` 0；`sessionPersistence` 有 3 个插件注入它，但不构成阻塞原因，需要核对具体用法）。系统提示整体改写与模型请求拦截在样本中各只有 1 个或 0 个插件（dsh-purge 在样本之外单独分析）。

**两个指定样本。**
- **dsh-rea 1.2.0**：旧扫描器只记录了 `tools`（`tools.schemas`）读取，14 项被归为已接通、未记录阻塞；新宿主仍须完成实际工具业务验收。它把上游 REA 的 MCP 服务注册为 `mcp__rea__*` 工具。

## 7. 公共能力分组

第 6 节的 113 行是 DSH 的服务清单，不是 Magi 要新增的 113 个服务。Magi 按真实任务形成少数几项公共能力；Node 插件宿主按 DSH 合约实现这些服务，背后调用这些能力：

| 公共能力 | 涵盖的 DSH 接缝 | 依据 |
| --- | --- | --- |
| 会话读取与事件 | `sessions`、`agents`（句柄）、`sessionProjections`、`sessionQuery`、`workspaceRegistry`、`session/event`、`agent/created`、`goals` 读取、`planMode` | 样本被阻塞的首要原因 |

项目级 Super-agent 设计（`docs/magi-project-super-agent-and-upstream-maintenance-design.md`）计划让插件参与持续观察外部事件、主动工作和交付跟进，这支持“会话事件、凭据、持久业务数据、调度、执行”这几项能力的方向；但它是规划，不是已交付，也不是本表的需求来源，需求来源是第 5 节的真实插件。


## 8. 界面槽位对齐

DSH 的界面是**槽位系统**：宿主和各界面包声明槽位，插件的客户端部分把组件注册进去。DSH 发行的网页客户端共声明 **122 个槽位**（来自其 `slot-catalog` 生成清单）：对话区 47、侧栏 29、设置 14、插件管理 9、代码托管 5、外壳 4、工具 3、其余 11。

### 8.1 范围（决策 7）

**范围内：设置页、主页面、右栏标签页。** 范围外的槽位（主对话的输入区、对话区、工具调用视图、会话头部，左栏，外壳浮层，以及它们的替换类）暂不支持，先对齐核心接缝，后续有条件再评估。

**Magi 的设置页就是槽位的承载位置。** 每个插件在设置里有独立页面：左侧导航里一个入口，页面顶部是 Magi 原生页头（图标、名称、版本、启用开关、卸载），正文由插件注册的组件渲染，例如 WorkBuddy 的账号池、更多设置、活动记录都是它自己的组件。DSH 的 `settings.section`、`plugins.bundle.config`、`settings.plugins.tab` 与全部 `plugins.*` 槽位都渲染在这里，沿现状，不新增位置。

### 8.2 Magi 现状

槽位表（`scripts/compat/runtime/client/slot-context.mjs`，核对的是 DSH 0.2.2-rc.1）登记了 18 个：
- **6 个挂载**：主页面 `main`、设置 `settings.section`、`settings.plugins.tab`、`plugins.tab`、`plugins.bundle.config`、右栏 `sidebar.right.pane.tab`。
- **5 个别名（现状：组件被接收，但不按合约渲染，由别的槽位或清单数据代替）**：`settings.section.icon`、`plugins.row.config`（与 `plugins.bundle.config` 是同一个配置组件）、`sidebar.panellist`、`sidebar.right.pane.tab.title`、`sidebar.right.tab.guide.entry`（右栏标签的名称与导航）。
- **3 个接收但内容不显示（现状：静默丢弃，没有告诉用户）**：`sidebar.footer.action`、`conversation.input.left`、`conversation.input.right`。
- **2 个拒绝安装**：`conversation.chat.node`、`conversation.input.dock`。
- **2 个明确未接入**：`conversation.session.header.actions`、`conversation.chat.turnTail`。其余槽位没有登记。

**关键事实：安装时只要插件注册了既不挂载、也不是别名或忽略的槽位，安装就会直接失败**（提示“该插件需要尚未接入的界面位置”）。DSH 当前 master 的槽位与 rc.1 有出入，下表以 master 为准。

**目标规则（取代别名与静默丢弃）**：范围内的槽位，插件注册的每个组件都按 DSH 合约在对应位置渲染；同一个组件注册到两个范围内槽位时，渲染位置相同的只渲染一次，不同组件各自渲染。范围外的槽位按 8.4 接收、不渲染，并在安装预览与详情里明示。不再有“别名”“接收但静默不显示”。

### 8.3 历史槽位统计（样本 95 个包，对注册调用做静态匹配）

以下“安装失败”“通过”等均为旧规则下的扫描分类或推算，不是新平台实测结果，也不用于决定新平台安装准入。

- 45 个包注册了界面槽位。其中 25 个全部落在“挂载、别名或忽略”里，**20 个（44%）至少注册了一个会让安装失败的槽位**。另有 6 个因使用“接收但不显示”的槽位，能安装但丢失对应内容。
- 导致安装失败的槽位（插件数）：`shell.overlay` 6，`plugins.item` 5，`conversation.input.dock` 4，`tool.call.toolview` 4，`conversation.view` 3，`conversation.chat.node` 2，`plugins.detail.section` 2，其余各 1。
- 按位置归类（受影响插件数，可重叠）：插件管理页 8、对话区 7、输入区 6、外壳浮层 6、工具视图 4、设置页 1。
- **其中属于范围内的只有插件管理页（`plugins.*`）和设置页**：登记并渲染后，样本里有 5 个只因这类槽位被拒的插件即可通过。其余都在范围外。
- 合并后端：79 个已扫描插件中，后端无阻塞 50 个；这 50 个里 7 个会被范围外的槽位拒绝，其中 3 个只是因为 `plugins.*`。按当前规则，两项都通过的是 43 个（54%）；若把 `plugins.*` 补上，是 46 个。这是安装准入，不是业务验收。

### 8.4 范围外槽位与无页面插件的规则（已定：允许安装并明示缺失）

运行与动态注册**采用同一条规则**：范围外槽位的注册被接收但不渲染，插件照常运行。槽位在运行时注册，安装前无法确知，因此安装预览只展示包信息与 Magi 的支持范围，并标明“界面位置激活后检查”（第 3.4 节）；**激活后，插件详情依据真实注册列出“该插件的 N 项界面功能在 Magi 中不可用”及具体槽位**，之后动态新增的注册同样更新。其余功能（后端、设置页、主页面、右栏）正常。这类插件不算“完整运行”，缺失要如实展示。

**没有可显示的页面，也不能因此否定仍然可用的工具或模型业务。** 只提供工具、模型数据源、命令或后台能力的插件，没有任何挂载槽位时照常安装、激活与运行；插件列表与详情明确显示“该插件没有设置页面”，不显示空白页，也不当作安装失败。

这改变了现有行为：当前 `client-assets.mjs` 对未登记槽位直接抛错，对“没有任何挂载槽位”也抛错（“不交付空白设置页”）。`client-assets.mjs` 属于第 3.4 节的删除清单；槽位在运行期注册时判定范围，依赖旧行为的验收与文案同步更新。

旧扫描分类不能推导新平台的安装、激活或业务成功数量。范围外槽位的缺失说明只描述已观察到的注册；每个插件的实际业务结果按第 10 节验收。

### 8.6 标准套件（组件可调用的 hook）

DSH 的标准套件是可合并的接口，由各客户端包向其中合并 hook（`ui-slots` 的 `GlobalStandardProps`、`SessionStandardProps`、`SessionMaybeStandardProps`）。按 DSH 标准网页客户端的组成，核对源码得到：

| 层 | 交给谁 | hook 与属性（来源包） |
| --- | --- | --- |
| 全局 | **每个槽位组件，包括设置页与主页面** | `useSessions`、`useSessionRetainInfo`、`useSessionAccess`（ui-session）；`useWorkspaces`、`useWorkspaceAccess`、`workspace`（ui-workspace）；`useSessionStatus`、`sessionStatus`（ui-session-status）；`useResource`、`resources`（resources）；`usePanelInfo`（ui-layout）；`useContextMenu`（ui-context-menu）；`useRemoteAccess`（remote-access） |
| 会话 | 会话作用域槽位，例如右栏标签页 | 在全局之上加：`useSession`、`sessionId`、`useProjection`、`useAccess`（ui-session）；`useChat`、`chat`（ui-chat）；`useTrajectory`（ui-trajectory）；`useConversation`、`useInput`、`inputActions`（ui-conversation） |
| 可选会话 | 可能没有会话的槽位 | 同会话层，值可以为空 |

**实现现状（2026-11-19）与取舍的修订。** 逐包核对锁定 SDK 后，原先“全部挂载真实客户端包”的路线不成立，修订为：**能力服务挂载真实包；与 DSH 应用外壳绑定的 hook，由 Magi 外壳按 DSH 合约的精确形状、用外壳自己的真实事实提供；没有事实来源的 hook 不提供，不返回假值。** 依据：
- `ui-layout` 注册 DSH 的整套应用框架，与决策 7 冲突；`ui-workspace` 依赖它和未发布到 npm 的 `ui-session-status`，不能挂载。
- `ui-session` 依赖会话控制器客户端，后者经 `remote.session`（约 25 个方法，含 `control`、`follow` 流）、`remote.commands`、`remote.subagents` 取数；这些合约的 DSH 服务端以整套 DSH 会话核心为对等依赖，Magi 要实现的是一个完整的 DSH 会话 API 网关，规模是独立项目，列入阶段 2 的剩余工作，不在页面宿主里用外观代替。

已交付（均有测试，未做真机验收）：
- **访问判断**（真实包）：服务端用真实 `@deepseek-ai/dsh-api-remote-access`，客户端挂载真实 `remote-access/client`，会话与工作区访问是 `ctx.remoteAccess.source(kind, id, action)` 的真实可观察源，无快照时答 `false`。
- **资源**（真实包）：真实 `@deepseek-ai/dsh-client-resources`，状态为合约的 `none | loading | live | failed`。
- **会话列表与保留信息**（合约精确的外壳事实）：`useSessions` 是 `SessionListState`（`ids`、`byId`、`phase`、`projectionsBySession`），行里的 `running`、`updatedAt`、`blank`、`cwd`、标题都来自外壳的会话目录；`retainedBy` 只在会话于主视图打开时为 `{mainView:1}`；`useSessionRetainInfo` 是 `{referenceCount, retainedBy}`。成员没有事实来源时省略，例如没有标题时 `displayTitle` 取项目目录名、再取 id，`messageCount` 未知时 `blank` 取保守值 `false`。
- **面板信息**：`usePanelInfo` 是 `{activePanelId}`，仅当页面是主页面时指向该视图。
- 已删除的假实现：恒放行的访问对象、`unavailable` 资源状态、空函数 `useContextMenu`、恒为 `false` 的 `running`、凭空合成的 `retainedBy`、状态缺失时填的 `idle`、形状不符的会话状态与工作区快照。

当前不提供（调用会明确失败，不静默）：`useSession` 及会话作用域的投影、聊天、轨迹、会话与输入成员；`useSessionStatus`（缺 `completionFailed`、待处理交互的事实，且真实包未发布）；`useWorkspaces`（缺归档、置顶与排序事实）；`useContextMenu`（真实包需要 `shortcuts`，弹层注册在 `shell.overlay`，Magi 根外壳不渲染该槽位，而设置页与右栏 iframe 按内容高度自适应会裁掉弹层，需先按 UX/UI 规范定弹层位置）。

仍是手写外观、待核对或随会话服务替换的三处：`locale`（真实 `client-locale` 会把语言写入 DSH 设置，与 Magi 自有的语言偏好是两个事实源，需先定归属）、`commandUi`（真实 `ui-commands` 依赖会话服务）、`typert` 客户端注册表。

**交付规则：** 标准套件是槽位合约的一部分。某一层没有完整提供，依赖这一层的槽位就不算交付，不做只实现一部分就上线。**全局层交给每个槽位，所以连设置页也依赖会话目录、工作区、会话状态、访问判断、资源、上下文菜单和面板信息**，它们属于第 10 节第 1 阶段的最小依赖闭包。会话层随第 2 阶段交付。

样本用量（95 个包，静态匹配，仅作排序参考）：`useSession` 6、`useSessions` 5、`useProjection` 4、`inputActions` 4、`useChat` 与 `useInput` 各 2、`useWorkspaces` 1、`useSessionStatus` 1，其余为 0。

## 9. 执行循环与会话存储后端

两者在 DSH 中都是可替换接缝。架构位置现在确定，实施按源码审计结论推进；**不用镜像代替真实后端**：镜像只服务备份或导出，如果有这个需求要单独立项，不作为存储接缝的过渡方案，也不算存储接缝完成。

**`ctx.agentLoop` ↔ Magi 外部执行器接口（2026-11-20 源码审计与落地）。** 审计 `crates/magi-app-server-protocol/src/generated.rs::ExecutorCapabilities` 与 `crates/magi-conversation-runtime` 确认：Magi 已有完整的能力声明（输入模态、`steer`、`resume`、`tools`、`approvals`、`cancellation`、`context: magi_owned | executor_owned`、`background`、`inspection`），且 `tool_execution_ledger` 已强制隔离 `executor_owned` 与原生模型重放、子代理已隔离目录。共享宿主在 `execution-seams.mjs` 落地了 `ctx.agentLoop`（`MagiAgentLoopService`）：支持插件注册、列举、选择、运行、取消、恢复自定义执行循环；遵守 3.1 合同（重名冲突拒绝、撤权自动清理、显式选中循环不可用时明确报错绝不静默回退）；未选外部循环时走 `magi-native`（由 daemon 掌握租约、取消与观察）。

**`ctx.sessionPersistence` ↔ 会话存储后端（2026-11-20 源码审计与落地）。** 审计 `crates/magi-session-store/src/store/mod.rs::SessionEventWriter` 与 `SessionEventLog` 确认：Magi 的主会话持久化事务与 `SessionStore` 内存权威状态、`CanonicalTurnMutation`、`SessionInputMutation`、`SessionAcceptanceRecord` 及 `Task` 强耦合，并由 daemon 持有唯一本地文件锁；因此**不做** Node 侧影子镜像替换 `magi-session-store`。在此基础上：
- `ctx.sessionPersistence` 默认继续严格以只读模式呈现 daemon 权威会话日志（`create` / `open('write')` 抛官方 `SessionReadOnlyError`）；
- `execution-seams.mjs` 新增受控后端接缝 `ctx.sessionPersistenceBackends` 及完整实现 `@deepseek-ai/dsh-session-persistence` 合同的标准 JSONL 单写者后端 `createJsonlSessionPersistenceBackend(dir)`（支持 `create`、`open(id,'read'|'write')`、单写者独占锁 `SessionAlreadyOwnedError`、`assertStoredId`/`assertContiguous`、逐批 `fsync` 与显式 `flush` 屏障、`stat`/`list`、句柄关闭守卫 `SessionHandleClosedError`），供需要独立可写会话域的插件或测试显式使用，绝不静默切换后端或影子镜像 daemon 日志。

## 10. 推进阶段与退出条件

主线：先完成 DSH 原生插件宿主与运行时合同，再用固定原包的真实业务任务验收，验收通过后在同一阶段删除旧 SDK 2 公开接口与翻译实现。界面只做决策 7 的范围。

**每个阶段都写明六项：** 唯一目标、固定样本（原包名与版本在阶段开始时锁定）、必须通过的业务任务、允许保留的“不提供”服务、旧路径删除清单、进入下一阶段的条件。激活成功数只作辅助指标，不作为验收结论。

**固定样本与证据文件。** 每阶段开始时建立 `docs/plugin-validation/phase-<N>/manifest.json`，记录实际 npm 包名（不能仅用显示名称）、精确版本、包来源及 tarball integrity（本地包记录内容摘要）、解析后的依赖锁文件及摘要、DSH 上游提交与 SDK 版本、Magi 提交或构建身份、能力基线、平台与验收环境。更新用例分别锁定更新前后的原包版本和摘要。任务清单及运行结果保存在同目录，逐包列明用户操作、预期结果、实际结果、证据位置和未运行项，不包含凭据。执行前核对包与依赖摘要；包内容或依赖变化即形成新的基线和验收记录，不能覆盖旧结果或混合不同批次宣称通过。这里规定的是阶段开始时要生成的证据，不表示文件或验收已经存在。

**通用业务任务**（对样本中适用的包逐项执行，在真实 Electron 与 daemon 中完成）：激活；工具或命令执行；模型调用；设置保存与重新读取；页面交互；停用与重新启用；在线更新；宿主崩溃后的恢复；适用时的取消与应用重启后的恢复。
